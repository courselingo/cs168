## 一、数据中心为什么不一样

上一讲设计了 Clos 网络，它的特点是服务器之间有很多条路径，可以让多台服务器同时以高带宽通信。这一讲要解决的是：我们此前那些[[term:routing]]协议，放到这种拓扑上会浪费掉什么。

答案很直接：它们只挑一条路。

> "So far, our routing protocols pick a single path between a source and destination. If all our traffic uses the same path, we aren't taking advantage of all the extra links in the Clos network."
> （到目前为止，我们的路由协议在源和目的地之间只挑一条路径。如果所有流量都走同一条路，我们就没用上 Clos 网络里多出来的那些链路。）

教材给了两个具体的例子。第一个：假设 A 与 B 的上行[[term:bandwidth]]各是 200 Gbps，而交换机之间的[[term:link]]是 100 Gbps。如果 A 与 B 之间的流量全被塞进同一条路径，另一条路径就白白闲着；如果允许分组走不同的路，我们本可以跑满速率。

第二个例子换了个角度：所有链路都是 100 Gbps，此时有多个连接在抢带宽。如果 A-B 与 C-D 两个连接都挑了同一条路径，那么那条路上的两段链路会被压到 200 Gbps，而它们的容量只有 100 Gbps。让这两个连接走不同的路，本来就能各自跑满。

![两条路径只走一条：另一条链路白闲着，上行走廊也被压住](figures/datacenter-routing-1.svg)

这两个例子合起来说明：问题不是「找不到路」，而是「找到了却只肯用一条」，而 Clos 的代价正是为了让路变多。

![多个连接抢同一条路：两条各 100 Gbps 的流量压在一条 100 Gbps 的链路上](figures/datacenter-routing-2.svg)

两个例子的形状是同一个：链路在，路也在，只是转发时没人肯分开走。

## 二、等代价多路径：目标与那个函数

**等代价多路径（Equal Cost Multi-Path，ECMP）**的目标是：找出所有代价相同的最短路，然后把分组在这些路之间做负载均衡。

于是问题落到一台[[term:router]]身上：[[term:packet]]到了，若有多条出链路都通向合法的最短路，该挑哪条？教材把它写成一个函数。

> "The router needs some function (think of it like a piece of code) that takes a packet, and outputs a choice of link."
> （路由器需要一个函数，可以把它想成一段代码，输入一个分组，输出一条链路的选择。）

这个函数还必须真的把流量均摊开，不能名义上有两条路、实际上还是挤在一条上。

![ECMP 把选择写成一个函数：输入分组，输出一条出链路](figures/datacenter-routing-3.svg)

接下来两节就在讨论这个函数该怎么写：先看一个看似自然的做法为什么会坏，再看怎么用首部字段把它写对。

## 三、轮流发为什么不行

最自然的想法是**[[term:round-robin]]**：有两条最短路出链路时，让奇数分组走链路 1、偶数分组走链路 2。

它的问题在于把两件事混成了一件：等代价并不等于等时延。代价是运营者用自己挑的度量定义的，两条代价相同的路完全可能一快一慢。

> "If we send all odd packets along a slow link, and all even packets along a fast link, then the TCP recipient might end up receiving all the even packets before the odd packets."
> （如果奇数分组走慢链路、偶数分组走快链路，TCP 接收方可能会在收到奇数分组之前就收齐了全部偶数分组。）

而 TCP 很在意乱序：接收方只能把先到的偶数分组缓冲起来，等缺的奇数分组到齐，性能因此变差。换个角度看，教材前面的课里已经讲过，可靠传输本身就要对付乱序，而这里是我们主动制造乱序。

![轮流发把同一连接的分组拆到两条时延不同的路上，接收方只能缓冲等待](figures/datacenter-routing-4.svg)

结论是：不能按「第几个分组」来分，得让同一个连接的分组始终走同一条路。怎么知道两个分组属于同一个连接，就成了下一节的问题。

## 四、从单个字段到**五元组**

既然要确定性，就去看[[term:header]]字段。教材把候选字段一个个试过来，每一步都指出漏在哪。

只看[[term:ip-address]]不行：很多源都把分组发给同一个目的地时，所有分组的目的 IP 相同，于是全被映射到同一条链路，均衡无从谈起。只看源 IP 也不行，只是把场景翻过来而已：一个源往很多目的地发，源 IP 相同，同样都挤在一条路上。

把两者一起看就够了：把源与目的 IP 一起哈希，再把哈希结果映射到链路（和哈希表的做法类似）。教材给的理由是**熵**：源与目的 IP 合起来，足以避开「同一源」或「同一目的」各自塌到一条路上的情形。

还剩最后一个漏洞：同一个源与同一个目的之间可能有多条大连接，这些连接的两端 IP 完全一样，只靠 IP 哈希仍会全落到同一条路。补法是把 TCP 或 UDP 首部里的源端口与目的端口也算进来。

一般化的说法是：把每个连接放到单独的链路上，前两类问题就都不存在了。而要唯一标识一个连接，需要五个值。

> "To uniquely identify a connection, we need a 5-tuple of: (source IP, destination IP, protocol, source port, destination port)."
> （要唯一标识一个连接，我们需要一个五元组：源 IP、目的 IP、协议、源端口、目的端口。）

这里的[[term:protocol]]不能省：同样的 IP 与端口，一个是 TCP 连接、一个是 UDP 连接，它们是不同的连接。教材给了一句很硬的话：两个分组属于同一个连接，**当且仅当**它们的五元组相同。

把这五个值一起哈希，就得到两个想要的性质：同一个连接的分组走同一条路径（不会乱序），不同连接则被分散到不同路径上（这才叫均衡）。这种做法常被称为按流[[term:load-balancing]]（per-flow），而现代商用路由器通常内建了读取这五个值的能力。

它也有自己的边界：均衡的是连接的数量，不是连接的大小。教材说，把大小也算进去技术上可行，但路由器要做更多工作，而收益不大（按流做已经能把不同大小的连接摊得比较匀），所以实践中不做。

![单个字段不够：目的 IP 与源 IP 各自会塌；五个值一起哈希才唯一锁定一个连接](figures/datacenter-routing-5.svg)

从「按分组」到「按连接」，是这一讲最要紧的一次换位：均衡的单位变了，乱序的来源也就消失了。

![五元组与按流均衡：同一条流走同一条路，不同的流被摊到不同的路](figures/datacenter-routing-6.svg)

这条规则不挑应用：跑在 IP 之上的 HTTP 与 DNS 都同样受益于「同一条流不乱序」。

## 五、多路径的距离向量协议

要让带宽跑满，就得让去同一个目的地的分组也能走不同的路（比如它们属于不同的连接）。这意味着要改路由协议，让路由器学到所有最短路，而不是只学一条。

标准距离向量里有一条规则恰好挡在这里：收到一条代价与已知最优相等的新路径广告时，我们是不接受它的。要记住所有最小代价路径，就得把这一条翻过来：接受这条等代价路径，并把两条都存进[[term:forwarding]]表。

> "In the forwarding table, a destination can now be mapped to multiple next hops, as long as they all have the same minimal cost."
> （在转发表里，一个目的地现在可以映射到多个下一跳，只要它们的最小代价相同。）

教材的例子是：R1 同时收到 R4 与 R3 的广告，两者都说自己能用 2 跳到达 B；于是 R1 的表把 R4 与 R3 都存成可能的下一跳，最小代价都是 3。

（就地说明） 原文同一段后面那句写「把大约一半的连接发给 R3，另一半发给 R2」，而原文给这一节的配图里，表写的是「经 R2、代价 2」与「经 R4、代价 2」。于是三处对不上：正文的 `{R4, R3}` / 代价 3、同一段那句的 `R2`、配图的 `{R2, R4}` / 代价 2。按正文的叙述（广告里的 2 跳加上到邻居的 1 跳（这条规则与第 10 讲距离向量里那条是同一条））应为 R4 与 R3、代价 3。我们照录正文的写法并在此说明，供平台判据留存。

转发的时候，路由器把五元组哈希：大约一半的连接走其中一个下一跳，另一半走另一个。

![多路径距离向量：相等就接受，一个目的地存多个等代价的下一跳](figures/datacenter-routing-7.svg)

改动其实只有一处，但位置关键：在「相等就不接受」这一句上翻了面，于是表从一对一变成一对多。

## 六、多路径的链路状态协议

链路状态协议靠泛滥让每台路由器都拿到完整的网络图，正常情况下每台算出一条到各目的地的最短路，据此填表。要支持多路径，就要让每台算出所有最短路。

> "As in the modified distance-vector protocol, the forwarding table can now contain multiple next-hops for a given destination."
> （和改过的距离向量协议一样，转发表里一个目的地现在可以有多个下一跳。）

两类协议的改法在技术上是不同的，一个改的是「收到等代价广告怎么办」，一个改的是「算一条还是算全部最短路」，但落点完全一样：转发表的一项从一个下一跳变成多个，而且它们的最小代价必须相同。

![多路径链路状态：算的不是一条最短路，而是全部最短路](figures/datacenter-routing-8.svg)

这也是这一讲的收束：协议怎么改可以有两种，而它们必须共同保证的东西只有一条，代价相同的下一跳才允许并列。

## 读完应该能回答

1. Clos 网络里只走一条路会浪费什么，教材的两个例子分别浪费在哪。
2. 轮流发为什么会让同一个 TCP 连接出现乱序，为什么等代价不等于等时延。
3. 为什么只哈希源 IP 或只哈希目的 IP 都不够，五元组里的协议字段为什么不能省。
4. 多路径的距离向量与链路状态各改了什么，它们必须共同保证的那一条是什么。

## 脉络回顾

这一讲接着数据中心那一段往下走：上一讲用 Clos 拓扑把「服务器之间有很多条路」造了出来，而这一讲要解决的是怎么真的把这些路用起来。此前所有域内协议都只交付一条最短路，于是 Clos 换来的多路径在转发层面是闲置的，两个例子分别从「上行带宽 200 Gbps 却只吃 100」与「两个连接压在一条链路上」说明这件事。

解决路线分两半：转发层面用 ECMP，把「挑哪条链路」写成一个对分组求值的函数，而函数的正确写法从「按分组轮流」改成「按连接哈希」，因为等代价不等于等时延，按分组分散会亲手制造乱序，而五元组哈希让同一条流稳定走同一条路，同时把不同的流摊开。协议层面则是把「只记一条最短路」改成「记住所有等代价的最短路」，距离向量改的是接收等代价广告的规则，链路状态改的是计算全部最短路，两者都让转发表的一个目的地对应多个等代价下一跳。

最要紧的转折在均衡单位上：从分组级换到连接级。而后面讲到数据中心的拥塞控制时，还会回来依赖这里留下的「一个目的地多个下一跳」这个表结构。
